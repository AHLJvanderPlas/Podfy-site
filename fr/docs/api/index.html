Ce qu'est l'API

L'API ouverte PODFY permet à vos propres systèmes de lire les enregistrements (preuves de livraison et signalements QR), de mettre à jour leur statut de traitement et de gérer le registre de références (équipements). C'est une API REST JSON pour un usage de serveur à serveur. Il n'y a pas de CORS : appelez l'API depuis votre backend, jamais depuis un navigateur.

L'API ouverte est incluse dans PODFY Advanced. Si elle n'est pas active pour votre marque, chaque appel répond 403 feature_not_active. La spécification est au format OpenAPI 3.1 et la référence ci-dessous est générée à partir du même fichier.

Obtenir une clé API

Un administrateur de votre marque crée les clés dans le portail (en anglais), sous Settings → Integrations → API keys. Donnez un nom à la clé et choisissez ses scopes. La clé n'est affichée qu'une fois : conservez-la dans votre gestionnaire de secrets. Vous pouvez révoquer une clé à tout moment, et une clé révoquée cesse de fonctionner immédiatement.

  • records:read : lire les enregistrements
  • records:write : mettre à jour les enregistrements (autorise aussi la lecture)
  • references:read : lire le registre de références
  • references:write : créer et modifier des références (autorise aussi la lecture)

URL de base et authentification

L'URL de base est https://portal.podfy.net/api/v1. Envoyez votre clé comme jeton Bearer dans l'en-tête Authorization à chaque requête. Une clé ne fonctionne jamais comme paramètre de requête.

Une clé absente, mal formée, inconnue ou révoquée reçoit toujours la même réponse : 401 invalid_key. Une clé sans le scope requis reçoit 403 insufficient_scope.

curl -H "Authorization: Bearer $PODFY_API_KEY" \
  "https://portal.podfy.net/api/v1/records?limit=10"

Clés live et clés de test

Les clés qui commencent par pk_live_ ne voient que les enregistrements de production. Les clés qui commencent par pk_test_ (enregistrements QA uniquement) ne voient que les enregistrements de test de qa.podfy.app, dont les ID PODFY commencent par QA-. Les deux environnements ne se mélangent jamais.

Le registre de références est partagé avec la production : les clés de test ne peuvent donc ni créer ni modifier de références (403 insufficient_scope). Un enregistrement ou une référence d'une autre marque, ou un enregistrement de l'autre environnement, répond 404 not_found, jamais 403.

Limite de débit

Chaque clé peut effectuer 600 requêtes par minute, comptées par fenêtres fixes d'une minute. Chaque réponse contient X-RateLimit-Limit, X-RateLimit-Remaining et X-RateLimit-Reset (secondes unix de la fin de la fenêtre).

Au-delà de la limite, vous recevez 429 rate_limited avec un en-tête Retry-After (secondes). Attendez ce délai, puis réessayez.

Erreurs

Chaque erreur est un JSON de même forme : {"error":{"code":"…","message":"…"}}. Traitez les erreurs selon le statut HTTP et le code, pas selon le texte du message. Les réponses ne sont jamais mises en cache (Cache-Control: no-store). La liste complète des codes figure dans la référence ci-dessous.

Pagination

Les points de terminaison de liste renvoient {"data": [...], "next_cursor": "…"}. Renvoyez next_cursor comme paramètre cursor pour obtenir la page suivante, jusqu'à ce qu'il soit null. Les curseurs sont opaques : ne les construisez pas et ne les modifiez pas. Les enregistrements sont listés du plus récent au plus ancien. La taille de page se règle avec limit (de 1 à 200, 50 par défaut).
